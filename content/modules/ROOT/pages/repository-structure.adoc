= Repository Structure

The layout exists so that a reviewer, a script, and an agent can all find the same things in the same places. Every dashboard looks like every other dashboard.

[source,text]
----
rhoai-community-dashboards/
├── README.md                          <1>
├── dashboards/
│   ├── README.md                      <2>
│   └── <dashboard-name>/              <3>
│       ├── README.md
│       ├── perses/
│       │   └── <dashboard-name>.yaml
│       └── grafana/
│           ├── <dashboard-name>.json
│           └── <dashboard-name>-cr.yaml
├── validation/
│   └── scripts/
│       ├── validate_monitoring.sh     <4>
│       └── templates/                 <5>
├── content/                           <6>
│   ├── antora.yml
│   └── modules/ROOT/
│       ├── nav.adoc
│       └── pages/
├── supplemental-ui/                   <7>
├── site.yml
└── .skills/                           <8>
----
<1> Short introduction and links to this documentation site. Not the place for reference material.
<2> The xref:custom-dashboards.adoc#_dashboard_register[dashboard register], listing dashboards that live in other repositories.
<3> One directory per dashboard. The contract is below.
<4> Checks that the Monitoring Stack is deployed and ready. It validates; it never installs.
<5> Expected resource shapes: `DSCInitialization`, Grafana CRs, datasources. Product changes are absorbed here, not in the script.
<6> Antora source for this site.
<7> Theme overrides: logo, favicon, header and footer partials.
<8> Agent skills for contributing and deploying a dashboard.

== The dashboard directory contract

A directory under `dashboards/` is named after the dashboard in lowercase with hyphens (`vllm-performance-monitoring`, not `vLLM_Performance`) and contains:

[cols="1,3", options="header"]
|===
| Path | Requirement

| `README.md`
| Required. Purpose, audience, maintainer, tested versions, required metrics, deployment command, known limitations.

| `perses/`
| Required if a Perses version exists. One `PersesDashboard` manifest, applied as-is.

| `grafana/`
| Required if a Grafana version exists. Either a `GrafanaDashboard` resource with the dashboard inline in `spec.json`, or a dashboard `.json`. Both deploy with one `oc apply`, so both are accepted.
|===

At least one of `perses/` or `grafana/` must be present. Both is welcome; neither format is mandatory and the two are never checked against each other.

A directory holds exactly one dashboard. Two dashboards that are usually read together are still two directories, each deployable on its own.

== Why directories and not a flat tree

A flat `perses/` and `grafana/` pair at the repository root would be shorter, and it would mean that deploying one dashboard requires knowing which of a hundred files belong to it. With a directory per dashboard, the deploy command is derivable from the name:

[source,bash]
----
oc apply -f dashboards/vllm-performance-monitoring/perses/
----

That also makes the README unavoidable. A dashboard with no explanation of which metrics it needs is a dashboard that renders empty panels on someone else's cluster, and the directory is where that explanation has to live.

== One deployment path

Every dashboard deploys with `oc apply`. No Helm charts, no Kustomize overlays, no per-dashboard installation scripts.

This is a constraint on contributions, not a limitation of the tooling. A dashboard that needs orchestration to deploy is a dashboard with prerequisites beyond the Monitoring Stack, which means it belongs in the register rather than here. Keeping the deployment trivial is how the scope stays enforceable.

== What CI checks

Two layers run on every pull request, and they are deliberately separate.

=== Structural validation, which gates the merge

`validation/scripts/validate_dashboards.sh` runs in the *validate dashboards*
workflow. Every rule it enforces has exactly one right answer, so none of it
needs a language model:

* The directory layout matches the contract above. A dashboard directory with no `README.md`, or with neither `perses/` nor `grafana/`, fails
* `metadata.namespace` is `{monitoring-ns}`, because a `PersesDatasource` is project-scoped
* Every `datasource.name`, at any depth, is `{perses-ds}` rather than an ad-hoc one
* `metadata.name` matches `dashboard-99-<slug>[-admin]` and `display.name` carries the `[C] - ` prefix
* `apiVersion` is `{perses-api}`; `v1alpha1` is a warning rather than an error
* No query pins `model_name` or `model` to a literal where a variable would work
* Grafana directories hold a dashboard: a `GrafanaDashboard` CR whose `spec.json` parses, or a parseable `.json`

Run it yourself before opening a pull request. It needs `yq` and `jq`:

[source,bash]
----
./validation/scripts/validate_dashboards.sh
----

=== CodeRabbit review, which does not gate anything

CodeRabbit reviews every pull request and comments on the diff.
`.coderabbit.yaml` configures it, with path instructions that tell it not to
repeat the deterministic checks above. It is asked only for judgement a script
cannot provide: whether the PromQL is correct, whether a counter is plotted
without `rate()`, whether a `$ref` points at a panel that exists, whether a
variable is declared but never used.

Its comments are advice, not a gate. A maintainer decides what to act on.

It does nothing until the CodeRabbit app is installed on the organization,
which needs owner rights. It is free for public repositories.

=== Reviewing on our own model instead

`validation/scripts/ai_review.sh` sends the diff to a model running on our own
cluster rather than to an external service. The *ai review (manual)* workflow
runs it on demand:

[source,bash]
----
gh workflow run "ai review (manual)" -f pr=<number>
----

It is manual rather than automatic because CodeRabbit already covers the pull
request path and does it better, with line level comments, incremental review
on new commits and follow up questions. Running both automatically would mean
two bots commenting on everything.

Use it when a change should not go to a third party, or to demonstrate the
platform reviewing its own repository. Expect it to be slow: a 26 KB diff took
around two minutes and about 17,000 reasoning tokens, because the model reasons
before it answers.

NOTE: Hosted CodeRabbit reviews with CodeRabbit's own models in CodeRabbit's
cloud, not with a model you run. Connecting CodeRabbit to your own model
provider is a self-hosted feature, and self-hosted is limited to Enterprise
customers with 500 or more seats. That is why these are two separate things
rather than one configurable one.

=== What neither layer does

Neither checks that a Perses dashboard and its Grafana counterpart are
equivalent, and neither validates PromQL against a live cluster. Both need a
cluster with your metrics on it, which is the reviewer's job and yours.
